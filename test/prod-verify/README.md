# 生产验收脚本（人工触发，不在 CI 里跑）

这两个脚本对着**线上** mn-rt 与**线上**认证中心跑完整链路。它们需要真实账号口令，
因此刻意不接进 CI —— CI 里既没有口令，也不该每次构建都往生产注册表里写设备。

| 脚本 | 验什么 |
|---|---|
| `chain-check.cjs` | 登录 → 为 `mn-rt` 铸授权码 → PKCE 换 access_token → `/auth/verify` 换设备令牌+会话密钥 → `/my/devices` 按属主过滤 → **同一 code 重放必须被拒** → **换错 verifier 必须被拒** → 伪造令牌 401 |
| `push-check.cjs` | 真链路推送：手机侧用会话密钥封 RT1 信封 → 服务端路由 → PC 侧解密并产出按键计划 → ACK 回流被手机解开 → 明文帧被拒 → 用户令牌冒充 pc 被拒 → `/push` 本人令牌 forwarded |

## 跑法

```bash
# 认证中心地址默认 http://47.110.80.47:8082，被测服务端默认 127.0.0.1:8799
# 验生产必须显式指过去：
GOAH_USERNAME=<账号> GOAH_PASSWORD=<口令> \
  RT_CHECK_LOCAL=http://1.94.101.189:8790 \
  node test/prod-verify/chain-check.cjs

GOAH_USERNAME=<账号> GOAH_PASSWORD=<口令> \
  RT_CHECK_LOCAL=http://1.94.101.189:8790 RT_PC_ID=my-pc \
  node test/prod-verify/push-check.cjs
```

口令只走环境变量：不写进文件、不提交、不打印（输出里也不出现）。

## 退出码约定

`0` 全通过 / `1` 有断言失败 / `2` 脚本自身异常 / **`3` 没配口令，整组未执行**

`3` 是刻意分开的：这两个脚本没口令时必然什么都测不到，如果那种情况报 0，
"没执行"在人和流水线眼里就都长得像"测过了"。

## 会往生产写什么

`chain-check` 登记 clientId `chaincheck-pc`，`push-check` 登记 `RT_PC_ID`（默认
`prod-e2e-pc`），都在你账号名下，各自带一把会话密钥，落进容器的 `devices.json`。
目前**没有注销设备的接口**，所以这些记录会累积 —— 无害（只影响你自己的列表），
但别指望它们是干净的空表。

## 为什么值得留这两个脚本

这一类链路的失败全是**静默**的：接口照样 200、结构照样合法，只是解不开或属主不对。
单元测试用打桩绕过了认证中心那几跳，离线端到端用同密钥自签令牌也绕过了，
所以"和本地实现一致"不等于"和线上认证中心互操作正确"。
只有真的敲一次线上，才知道 code 能不能重放、verifier 换了对面认不认。
